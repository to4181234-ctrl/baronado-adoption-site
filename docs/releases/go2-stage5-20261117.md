## 실제 코드 변경 및 기존 기능 보존
- `components/GoBattle.js`: **랜덤 멍배틀** 기존 `Game`을 교체/삭제하지 않고 **친구 실시간 멍배틀** 모드 탭을 추가. 보유 카드 목록, 랜덤 상대 선정, 기존 Figma 배틀 충돌·승패 화면과 카드 삭제 규칙 등 기존 랜덤 로직 그대로. 초대 링크 `/go/battle?room=<uuid>`로 열면 친구 모드 우선.
- `components/GoFriendBattle.js` / CSS, `lib/goPvpRules.js`, `lib/goPvpInvite.js`, `app/api/go/pvp/route.js`: 과거 main의 이미 구현되어 있던 친구 초대방/12자 코드·UUID 링크, 실시간에 준하는 **2.5초 폴링** 동기화, 개인별 보유 나만의/공식 일반 카드 선택, 두 명 READY→동시 공개, 파워+애교 합계(동점=무승부, 속성 상성 없음), 서버 서명 이미지, 4.28초 배틀 효과/소리·진동, 최대20개 과거 개인 전적/누적 승무패, 상호 동의 재대결, 로그아웃·재진입 시 기존 룸 복구를 **중복 개발 없이 재사용**. `MEONGGO_STAGE5_PVP_ENABLED`과 `NEXT_PUBLIC_MEONGGO_STAGE5_PVP_ENABLED` 5차 플래그로 분리(구형 stage3 PvP 플래그는 재사용하지 않음).
- 5차 추가 교정: 초대방 준비 중 상대가 6초간 폴링 중단하면 DB가 두 명의 READY 상태를 해제. 30초 미복귀 시 서버가 방을 취소. `go_pvp_snapshot` 응답 `otherConnected`, `reconnectDeadline` 신설. 브라우저에서 남은 초·재준비 안내 및 상대 부재 동안 준비 버튼 비활성. 종료된 대결/보상은 다시 쌓지 않는다.
- `app/api/go/battle/route.js`: 기존 랜덤 배틀 기록 생성/재조회 뒤 `go_battle_reward_random` 원자 RPC를 호출, KST 날짜별 유일한 `quest:battle:YYYY-MM-DD` source key로 +10C. **친구 PvP 기존 DB에서 지급하는 +10C와 같은 source key** 사용하므로 합산 중복 없음. 클라이언트 `GoBattle.js`는 실제 보상 후 헤더 지갑 새로고침.
- `components/GoQuests.js` / `GoCoins.js`: 네 번째 퀘스트 문구와 거래 유형을 ‘친구 또는 랜덤 멍배틀 첫 완료’로 수정, 기존 1~4차 퀘스트와 지갑 보존.

- `app/figma-stage5-battle.css`: 원본 배틀 레이아웃이나 아트 수정 없이 모드 탭과 재접속 상태만 한정 추가.

## 운영 미적용 SQL과 중요한 배포 전제
- `docs/sql/stage5-friend-pvp-and-random-battle-DRAFT.sql`(약 22KB): 기존 운영DB를 읽기 전용으로 분석해 이미 존재하는 `go_pvp_rooms` / `go_pvp_rounds` / `go_pvp_records`, `go_pvp_has_card`, `go_pvp_card_snapshot`, `go_pvp_create`, `go_pvp_join`, `go_pvp_action`, `go_pvp_snapshot` 정의를 **검토용 통합 마이그레이션 초안**으로 작성. 준비 중 연결 중단 시 양쪽 READY 해제 + 30초 취소, 상대 카드의 공개 전 이미지·능력치 비노출 보존. 회원별 완료 기록 중복 방지 유니크 키, RLS 설정, `anon/authenticated` 권한 차단 및 `service_role` 제한 권한. 기존 스키마의 갱신·삭제는 수행하지 않는 설계.
- 새 RPC `go_battle_reward_random`: 본인의 서버 저장된 `go_battles` 기록에 대해서만 +10C, 지갑 행 잠금 및 source key 충돌 시 +0C 응답, 누적 반복 적립 금지.
- 기존 5차 DB 테이블/함수는 운영 DB에 **이미 존재하지만 production 배포와 별도**. 마이그레이션 초안은 **운영에 실행하지 않았으며 사용자 최종 승인·백업 전 실행 금지**.
- 2차 4+HIDDEN1, 3차 지갑, 4차 상점 SQL과 5차 SQL을 공용 스테이징 DB에 순서대로 적용하는 **전차수 통합 테스트는 아직 안 했다**. 이 작업과 운영 백업/마이그레이션 순서 확인, 실제 Supabase Auth/Storage end-to-end는 운영 릴리즈의 남은 게이트.

## 검증 결과 — 실제 실행, 출처 및 한계
- Vercel 격리 Sandbox에서 5차 브랜치 checkout, `npm ci`, 1~5차 기능 플래그 ON 상태에서 **Node 자동 테스트 116/116 PASS, 오류0, Next.js production build PASS**. `tests/go-stage5-contract.test.mjs`가 Figma 30초/승부/결제·보상/슬롯1~4와 랜덤 기능 미삭제를 회귀 검사.
- 5차 전체 SQL 초안을 격리 PostgreSQL 18 `stage5qa`에 **실행 성공**, 재실행도 성공(레코드 4건 유지), `anon/authenticated` RPC EXECUTE 권한 false, `service_role` true.
- 실제 **두 개의 가상 회원이 DB 트랜잭션으로** 초대코드 생성→방 참가→각 소유 카드 선택→서버 본인 소유 확인→준비 완료→파워3+애교4 **7** 대 파워4+애교5 **9** 결과 ‘guest 승’ 및 참가자 각각 1건 전적 저장 확인.
- 같은 방 재대결에서 참가자 한 명의 마지막 폴링을 7초 전으로 이동→상대 연결 끊김과 양쪽 READY 해제 확인→같은 방에서 재접속→양쪽 다시 READY 후 2라운드 결과 저장. 반대로 31초 중단은 방 cancelled, 추가 전적/보상 **없음**.
- 랜덤 대결 +10C 선지급 후 친구 배틀을 추가 완료해도 같은 날 랜덤/친구 **합계 회원당 한 번**, 새로고침·서버 재조회에도 전적·보상 중복 없음. 기존 대결이 확정된 후 재조회 시 다른 승패를 선택하지 않는다.
- 공식 NO.1 소유자는 출전 가능, HIDDEN NO.5나 다른 회원 공식 카드·다른 회원 나만의 카드 출전 불가. 제3자 방 조회 금지, 카드 미선택 READY 거절, 상대 카드 이미지는 두 명 동시 확정 전까지 서버 반환 NULL.
- Playwright Chromium 320/390/430px: 실 서버 Next.js 화면 + 모의 API 기반으로 모드 전환→친구 초대방 생성→초대 코드 표시→친구 참가 표시→개인 카드 선택→READY, 모두 정상, 가로 넘침/JS 에러0. 기존 URL `?room=...`로 새로고침/다른 기기 참가 시 **친구 모드 자동 선택·기존 완료 결과/4.28초 연출 SKIP 복구 확인** (모의 응답). 브라우저에서 실제 두 회원이 **진짜 Supabase 권한으로 매칭한 HTTP E2E**는 운영/격리 인증환경 미구축으로 미진행.
- 기존 Figma `173:8009`은 기존 카드 2장 선택 및 충돌 디자인; 사용자 확정 추가 정책 주석 `617:163536`은 연결/보상/결과 보존. 친구 PvP의 완전한 새로운 픽셀디자인 Figma 프레임은 별도 확인되지 않았으며, 이전 앱에 구현되어 있던 스타일·폰트·충돌 효과를 재사용한다. 전 화면 완전한 픽셀 일치/실 사용자 네트워크 QA 주장 금지.
